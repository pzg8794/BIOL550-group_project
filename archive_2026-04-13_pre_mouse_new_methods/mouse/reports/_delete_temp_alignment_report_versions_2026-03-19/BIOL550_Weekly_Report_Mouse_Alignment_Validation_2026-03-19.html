Mouse RNA-Seq — Alignment Validation + Local Reproducible Analysis

BIOL550 — Weekly Report — Mar 19, 2026

What I accomplished since the previous report

This week, I moved the mouse project from QC remediation into alignment validation by analyzing the first full canonical STAR run for all 26 paired-end SRRs in PRJNA1017789 / GSE243308. To validate the server-side run independently, I set up a local reproducible analysis environment, copied the canonical STAR summary outputs into the project, and built a notebook-based alignment evidence package.

The local workflow parsed all 26 STAR Log.final.out files and all 26 STAR ReadsPerGene.out.tab files, then joined those alignment metrics to run metadata, sequencing-platform labels, and the earlier GC-WARN / GC-PASS classification. This produced a sample-level summary table, a reverse-stranded count handoff matrix, and a focused set of alignment figures.

The alignment results support moving forward. Across all 26 samples, the median unique-mapping rate is about 94%, the lower-performing subset still aligns well above failure territory, and the remaining platform / GC differences look like metadata to carry forward rather than reasons to stop the workflow. This week’s report therefore marks the transition from cleanup validation into count-level analysis and DE preparation.

Methods used

The alignment run used the canonical cleaned-input set generated from the full fastp workflow rather than the older FASTX baseline. Mapping was performed against the GRCm39 mouse reference with the matching Ensembl annotation, and the local report focuses on the STAR summary artifacts that are most informative for first-pass validation: the per-sample log metrics in Log.final.out and the special rows plus gene counts in ReadsPerGene.out.tab.

This analytical focus also follows the direction discussed in class over the last two days: once the GC-content split was shown to correlate with sequencing instrument rather than a simple biological subgroup, the next useful check was to compare alignment statistics across those platform-linked subsets and ask whether the GC shift behaves like a failed-sample issue or like a machine / batch effect that can be modeled downstream. 

Canonical alignment input:
- cleaned FASTQs from the full fastp rerun
- reference = GRCm39 + matching Ensembl GTF
- mapper = STAR

STAR index example:
STAR \
  --runThreadN 8 \
  --runMode genomeGenerate \
  --genomeDir star_index_sjdb150 \
  --genomeFastaFiles Mus_musculus.GRCm39.dna.primary_assembly.fa \
  --sjdbGTFfile Mus_musculus.GRCm39.115.gtf \
  --sjdbOverhang 150

STAR alignment example:
STAR \
  --runThreadN 8 \
  --genomeDir star_index_sjdb150 \
  --readFilesIn SRR30333743_1.trim.fastq.gz SRR30333743_2.trim.fastq.gz \
  --readFilesCommand zcat \
  --outSAMtype BAM SortedByCoordinate \
  --quantMode GeneCounts

Workflow used for local validation:

  • copy canonical STAR summary outputs locally;
  • parse all Log.final.out files;
  • parse all ReadsPerGene.out.tab files;
  • join alignment metrics with sample metadata;
  • summarize by sample, platform, and GC status;
  • export a count handoff matrix for DESeq2.

The local environment setup supported independent validation of the server-side STAR outputs in a notebook and made it possible to summarize the run reproducibly without repeated server-side reanalysis.

The local notebook now serves as the process record for alignment-stage interpretation and as the direct handoff into the DE notebook, where the reverse-stranded count matrix will be modeled with family-specific DESeq2 contrasts.

Results / key figures

Alignment overview: per-sample unique mapping across the full all-26 STAR run

This figure shows the unique-mapping rate for every sample in the canonical STAR run. The main result is that none of the samples collapse into a clear failed-alignment regime. Instead, the full set clusters in a high-mapping range with a median around 94%. That is the first strong indication that the data are technically usable for downstream expression analysis. The lower samples remain worth tracking, but they still sit in a range that supports keeping the complete dataset.

Even so, all groups remain within a technically usable range, which supports continuing with the full dataset rather than excluding one subset at the alignment stage.

Platform split at alignment: NovaSeq X performs somewhat better, but both platforms remain usable

The left panel compares unique-mapping rates across sequencing platforms and shows the same pattern visible in the sample-level overview: NovaSeq X aligns somewhat better than NovaSeq 6000. The right panel shows assignment burden after alignment, specifically the fraction of input reads that land in STAR’s N_noFeature and N_ambiguous categories. The point of showing both panels together is that the platform split is real, but it does not indicate a failed platform. Instead, the alignment results support the working explanation from the recent class discussion: the GC-content shift is at least partly tracking instrument / batch structure, and that structure remains visible after alignment as a modest platform effect that should remain explicit in downstream interpretation.

GC-WARN vs GC-PASS at alignment: weaker, but not failed

This figure addresses the earlier concern that the remaining GC-WARN subset might represent samples that should be removed before downstream analysis. The alignment result does not support that interpretation. The GC-WARN subset aligns somewhat worse than the GC-PASS subset, but it still maps at a high level overall and does not form a collapsed outlier group. In other words, the GC signal persists as a structured cohort effect, not as evidence that the samples are technically unusable. Because the GC-WARN samples also cluster strongly with the older sequencing platform, the alignment notebook helps explain the earlier GC bimodality as a likely platform-linked shift rather than a simple trimming failure.

Problems encountered

The main limitations at this stage are analytical rather than operational. First, the platform split remains visible at alignment, which means later differential-expression interpretation must keep platform as explicit metadata instead of assuming perfect homogeneity across all runs. Second, the GC-WARN subset still shows somewhat weaker unique mapping and somewhat higher multi-mapping, so that label should also be carried forward into the count-level and DE notebooks. Third, the local BAM / BAI copy from the server is still slower and larger than the log/count bundle, so the local notebook was intentionally designed to proceed using the completed STAR summary outputs first.

These issues do not block the project at this stage. The alignment results support proceeding with the full dataset while keeping platform and GC status explicit in downstream modeling and interpretation.
